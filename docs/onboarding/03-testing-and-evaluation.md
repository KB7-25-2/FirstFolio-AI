# 온보딩 3권 — 테스트와 성능 평가

> [1권](01-rag-pipeline.md) 검색, [2권](02-quiz-generation.md) 생성에 이어,
> 이 문서는 **"그게 진짜 되는지 어떻게 확인했는가"**를 다룬다.
> 발표에서 가장 많이 파고들 영역이므로 가장 자세히 썼다.

---

## 0. 두 종류의 "테스트"를 구분하는 것부터

이 프로젝트에는 성격이 완전히 다른 두 가지 검증이 있다.
**이걸 섞어 말하면 발표에서 반드시 꼬인다.**

| | 자동 테스트 (pytest) | 성능 평가 (measurement) |
|---|---|---|
| **묻는 질문** | "코드가 의도대로 동작하는가?" | "이 시스템이 얼마나 좋은가?" |
| **답의 형태** | 통과 / 실패 (이진) | Hit@5 = 0.92 (연속값) |
| **실행 비용** | 0원, 12초 | OpenAI 비용, 수 분 |
| **재현성** | 100% 동일 | 코퍼스·모델에 따라 변함 |
| **개수/규모** | **523개 테스트** | 26문항 세트 × 3종 |
| **실패 시** | 코드 버그. 고쳐야 함 | 판단 재료. 개선 우선순위 결정 |
| **다루는 곳** | 1~4장 | 5~8장 |

한 문장으로:
- **pytest는 "버그가 없는가"**를 본다.
- **성능 평가는 "품질이 어느 수준인가"**를 본다.
- 523개 테스트가 다 통과해도 검색 품질은 나쁠 수 있다. 반대도 마찬가지다.

# 1부 — 자동 테스트

## 1. 테스트 철학

### 1.1 무엇을 테스트하고 무엇을 안 하는가

**테스트한다**:
- 도메인 규칙 (문항 형식, 인용 규칙, 상태 조합)
- 알고리즘 (RRF 융합, 청킹 병합, 지표 계산)
- 경계 조건 (빈 입력, 하나만 있을 때, 초과할 때)
- **과거에 실제로 발생한 버그** ← 이게 제일 중요

**테스트하지 않는다**:
- OpenAI가 좋은 문항을 만드는지 (모델 성능은 우리 코드의 책임이 아니다)
- MySQL이 SQL을 올바로 실행하는지 (DB를 테스트하는 게 아니다)
- FAISS의 벡터 검색 정확도 (라이브러리를 테스트하는 게 아니다)

**경계는 "우리가 작성한 코드"**다.
외부 시스템은 우리가 그것을 **올바르게 호출하는지**만 검증한다.

### 1.2 외부 의존성을 실제로 부르지 않는 이유

```bash
docker compose exec -T ai-api python -m pytest
# → 516 passed, 7 skipped in 약 12초
```

523개 테스트가 **12초**에 끝난다. OpenAI를 실제로 부르면:

- 문항 1개당 API 2회 × 수백 테스트 = 수천 번 호출 → **비용 폭발**
- 네트워크 지연 → 수십 분
- LLM은 비결정적 → **어제 통과한 테스트가 오늘 실패**
- API 장애 시 CI 전체가 멈춤

마지막 항목이 특히 나쁘다. **테스트가 불안정하면 사람들이 테스트를 안 믿게 되고,
빨간불이 떠도 "또 그거겠지"하고 넘어간다.** 그 순간 테스트는 가치를 잃는다.

## 2. 아키텍처가 테스트를 가능하게 한다

이건 "테스트를 잘 짰다"가 아니라 **"테스트 가능하게 설계했다"**는 얘기다.
발표에서 설계 역량을 보여줄 수 있는 부분이다.

### 2.1 Protocol(포트)로 외부를 추상화

**코드**: [ports/](../../app/application/ports/)

```python
# app/application/ports/quiz_model.py
class QuizModelClient(Protocol):
    def generate_quiz(
        self, prompt: str, citation_candidates: Mapping[str, Sequence[str]]
    ) -> QuizModelResult: ...
    def validate_grounding(self, prompt: str) -> GroundingModelResult: ...
```

`QuizGenerationService`는 **`OpenAIQuizModelClient`를 모른다.**
`QuizModelClient`라는 **모양(shape)**만 안다.

```python
# app/application/quiz_generation.py:66-73
def __init__(self, settings, hybrid_search, chunk_repository,
             model_client: QuizModelClient,       # ← 구현체가 아니라 Protocol
             embedding_client: EmbeddingClient,
             rng: random.Random | None = None):
```

그래서 테스트에서 가짜를 넣을 수 있다:

```python
# tests/application/test_quiz_generation.py
model_client = Mock()
model_client.generate_quiz.return_value = QuizModelResult(quiz=..., input_tokens=10, ...)
```

**Python의 `Protocol`은 구조적 서브타이핑**이다.
`QuizModelClient`를 상속하지 않아도, 메서드 시그니처만 맞으면 타입 체크를 통과한다.
Java의 인터페이스처럼 `implements`를 선언할 필요가 없다.

포트가 3개 있다:

| 포트 | 실제 구현 | 테스트 대역 |
|---|---|---|
| `QuizModelClient` | `OpenAIQuizModelClient` | `Mock()` |
| `EmbeddingClient` | `OpenAIEmbeddingClient` | `Mock()` |
| `ChunkRepository` | `MySQLChunkRepository` | `InMemoryChunkRepository` |

### 2.2 InMemoryChunkRepository — Mock보다 나은 선택

**코드**: [in_memory_chunk.py](../../app/infrastructure/repositories/in_memory_chunk.py)

`ChunkRepository`만 `Mock`이 아니라 **진짜로 동작하는 인메모리 구현**이다.

**왜 Mock을 안 썼나**: `find_by_chunk_keys()`는 단순 조회가 아니다.
없는 키를 요청하면 `ChunkNotFoundError`를 던져야 하고, **요청한 순서대로** 반환해야 한다.

```python
# app/infrastructure/repositories/mysql_chunk.py:236-244
missing_chunk_keys = [k for k in chunk_keys if k not in chunks_by_key]
if missing_chunk_keys:
    raise ChunkNotFoundError(...)
return [chunks_by_key[chunk_key] for chunk_key in chunk_keys]  # 요청 순서 유지
```

이 동작을 `Mock`으로 흉내내려면 매 테스트마다 `side_effect`를 짜야 한다.
그럴 바엔 실제로 동작하는 구현 하나를 만들어 재사용하는 게 낫다.
이런 걸 **Fake(가짜 구현)**라고 하고, Mock과 구분한다.

> **원칙**: 상태가 없고 호출만 확인하면 되는 것 → Mock.
> 상태와 동작 규칙이 있는 것 → Fake.

### 2.3 난수 주입 — 비결정성 제거

```python
# app/application/quiz_generation.py:73, 81
rng: random.Random | None = None
self._rng = rng or random.Random()
```

`random`을 직접 부르지 않고 **주입받는다.**

TRUE_FALSE 목표 답(`O`/`X` 선택)과 선택지 섞기가 난수에 의존하는데,
이걸 주입 가능하게 해두면 테스트에서 시드를 고정할 수 있다.

```python
# 시드를 고정하면 매번 같은 결과
_service(rng=random.Random(42))
```

이게 없으면 `test_shuffle_quiz_options_reorders_and_tracks_correct_answer` 같은
테스트를 결정적으로 짤 수 없다.

### 2.4 시각 주입 — 같은 이유

```python
# app/application/quiz_validation.py:355
def stamp_scenario_market_reference_at(quiz: Quiz, now: datetime) -> Quiz:
```

`datetime.now()`를 함수 안에서 부르지 않고 **인자로 받는다.**
호출부에서만 실제 시각을 넣는다:

```python
# app/application/quiz_generation.py:126-129
quiz = stamp_scenario_market_reference_at(quiz=quiz, now=datetime.now(UTC))
```

테스트는 고정 시각을 넣어 정확히 검증한다
(`test_stamp_scenario_market_reference_at_overrides_model_value`).

> **일반 원칙**: **부작용(난수, 시각, I/O)은 가장 바깥으로 밀어낸다.**
> 안쪽 함수는 순수 함수로 유지한다. 그래야 테스트가 쉽다.
> 이걸 "함수형 코어, 명령형 셸(Functional Core, Imperative Shell)" 패턴이라고 부른다.

## 4. 테스트 유형별 상세

### 4.1 헬퍼 팩토리 패턴

모든 퀴즈 테스트가 이 구조를 쓴다.

```python
# tests/application/test_quiz_validation.py:76-81
def _quiz(question_type: str = "SINGLE_CHOICE", **changes: object) -> Quiz:
    payload = _quiz_payload(question_type)
    payload.update(changes)  # ← 바꾸고 싶은 것만 덮어쓰기
    return Quiz.model_validate(payload)
```

사용법:

```python
_quiz()                                          # 정상 문항
_quiz(usage_type="MAIN_CHAPTER")                 # usage_type만 틀린 문항
_quiz(options=[...3개만...])                      # 선택지 개수만 틀린 문항
```

**왜 이 패턴이 좋은가**: 테스트를 읽을 때 **"무엇이 다른지"만 보인다.**
정상 문항 전체를 매번 쓰면 30줄짜리 딕셔너리가 테스트마다 반복돼서
어디가 핵심인지 안 보인다.

### 4.2 파라미터화 테스트

```python
# tests/application/test_quiz_validation.py:105-110
@pytest.mark.parametrize("question_type", ["TRUE_FALSE", "SINGLE_CHOICE", "SCENARIO"])
def test_accept_valid_quiz_rules(question_type: str) -> None:
```

**한 번 짜고 3개 유형에 다 적용**한다.
새 유형이 추가되면 리스트에 한 줄만 넣으면 된다.

### 4.3 회귀 테스트 — 이 프로젝트의 특징

**"과거에 실제로 터진 버그"를 테스트로 박제**한 것들이다.
같은 버그가 두 번 나지 않게 하는 장치이고, **발표에서 가장 설득력 있는 부분**이다.

| 테스트 이름 | 박제된 사건 |
|---|---|
| `test_preserve_actual_overstrict_grounding_failure_fixture` | LLM 검증기가 오답 선택지를 이유로 정상 문항을 차단하던 실제 케이스 |
| `test_accept_actual_fixture_when_only_incorrect_distractors_lack_support` | 위 문제 수정 후, 이제는 통과해야 하는 실제 케이스 |
| `test_grounding_prompt_accepts_paraphrase_for_single_choice` | 검증기가 원문 복사만 통과시켜 "받아쓰기 퀴즈"가 되던 문제 |
| `test_grounding_prompt_allows_contradicting_evidence_for_true_false_x` | X 정답 문항이 "근거와 모순된다"는 이유로 전부 차단되던 문제 |
| `test_align_whitespace_only_citation_evidence_to_original_chunk` | 모델이 띄어쓰기를 고쳐서 정상 인용이 차단되던 문제 |
| `test_do_not_align_citation_when_non_whitespace_text_differs` | 위 수정이 **너무 관대해지지 않았는지** 확인 |
| `test_scenario_skips_all_numeric_check` | SCENARIO 가상 설정값이 수치 검증에 걸리던 문제 |
| `test_reject_when_another_option_can_also_be_correct` | 복수 정답 문항이 통과하던 문제 |
| `test_exclude_chunk_keys_pulls_up_next_candidate_within_pool` | 청크 제외 시 순위가 제대로 안 당겨지던 문제 |

**마지막 두 줄의 짝이 중요하다.**
`test_align_...`와 `test_do_not_align_...`은 **한 쌍**이다.
"관대하게 고쳤는데 너무 관대해지진 않았나"를 같이 검증한다.
버그를 고칠 때 반대 방향 테스트를 같이 넣는 습관이 있다는 뜻이다.

> **발표용 문장**: "수정할 때 통과 케이스와 차단 케이스를 쌍으로 넣습니다.
> 한쪽만 넣으면 완화한 검증이 어디까지 완화됐는지 알 수 없기 때문입니다."

### 4.4 프롬프트도 테스트한다

`test_quiz_prompts.py`가 30개로 두 번째로 많다. 프롬프트를 어떻게 테스트하나?

```python
# tests/application/test_quiz_prompts.py:178
def test_build_scenario_prompt_requires_natural_korean_persona_name() -> None:
    # 생성된 프롬프트 문자열에 해당 규칙 문구가 포함됐는지 확인
```

**"프롬프트에 이 규칙이 실제로 들어갔는가"**를 검증한다.

의미 없어 보일 수 있지만 아니다. 프롬프트는 **여러 조각을 조립**해서 만든다
(유형별 규칙 + 공통 규칙 + 기존 문항 + 스키마 + 근거).
조립 로직을 리팩터링하다가 **규칙 한 줄이 통째로 빠지는 사고**가 실제로 가능하다.
그러면 아무 에러 없이 조용히 품질만 떨어진다.

특히 중요한 것들:
- `test_limit_generation_evidence_to_top_five` — 근거가 5개를 넘지 않는가 (토큰 비용 직결)
- `test_exclude_sentence_containing_quote_from_citation_candidates` — 따옴표 문장 제외
  (2권 3.4절의 스키마 거부 문제)
- `test_separate_correct_answer_and_distractors_in_grounding_prompt` — 정답/오답 분리

### 4.5 경계 조건 테스트

```python
# tests/application/search/test_hybrid.py
test_return_empty_list_when_both_searches_have_no_results()  # 둘 다 결과 0
test_skip_faiss_search_when_faiss_weight_is_zero()  # 가중치 0
test_skip_bm25_search_when_bm25_weight_is_zero()  # 가중치 0
test_raise_error_when_faiss_chunk_key_does_not_exist()  # 정합성 깨짐
```

가중치 0 테스트는 **실용적 목적**이 있다.
검색 품질 실험에서 "BM25만" / "FAISS만"을 돌려보려면
가중치를 0으로 놓는데, 이때 **불필요한 API 호출이 안 나가는지** 확인한다.

```python
# app/application/search/hybrid.py:40-47
faiss_results = (
    self._faiss_search.search(...) if self._settings.faiss_weight > 0 else []
)
```

가중치가 0인데 검색을 실행하면 결과가 어차피 0점이라 무의미한데
**임베딩 API 비용은 나간다.** 그래서 아예 건너뛴다.

# 2부 — 성능 평가

## 5. 검색 품질 지표 — 개념부터

### 5.1 왜 검색을 따로 측정하는가

1권 0.3절에서 봤듯이:

```text
전체 품질 = 검색 품질 × 생성 품질
```

문항이 나쁠 때 **검색 탓인지 생성 탓인지 구분**할 수 없으면 개선할 수가 없다.
그래서 검색만 떼어내 측정한다.

### 5.2 평가 데이터 만들기

```json
// data/local/evaluation/search_cases_v2.json  (26개)
{
  "query": "가처분소득은 어떻게 산출하는가?",
  "relevant_chunk_keys": ["83:10"],
  "relevant_text": "가처분소득은 ..."
}
```

**정답 청크를 사람이 지정한다.** 이게 정답지(ground truth)다.

`relevant_text`는 보험이다:

```python
# app/application/search/evaluation.py:162-168
"""청킹 방식을 바꾸면 chunk_key가 전부 바뀐다. 평가 케이스에 저장해 둔
relevant_text로 새 코퍼스에서 같은 정답 청크를 다시 찾아
relevant_chunk_keys를 갱신하는 데 사용한다."""
```

1권 3.4절의 청크 병합을 하면 `chunk_key`가 전부 재발급된다.
그러면 평가 데이터 26개를 손으로 다시 만들어야 한다.
`relevant_text`(정답 문장 원문)를 저장해두면 `find_chunk_key_by_text()`로
새 코퍼스에서 자동으로 다시 찾을 수 있다.

**"평가 데이터를 재사용 가능하게 설계했다"**는 것 자체가 발표 포인트다.
이게 없으면 청킹 개선 전후를 비교할 수 없었다.

### 5.3 Hit@5 (= Recall@5)

**"상위 5개 안에 정답이 있는가"** — 있으면 1, 없으면 0.

```python
# app/application/search/evaluation.py:22-27
relevant_chunk_keys = set(case.relevant_chunk_keys)
top_k_chunk_keys = set(retrieved_chunk_keys[:k])
retrieved_relevant_count = len(relevant_chunk_keys & top_k_chunk_keys)
return retrieved_relevant_count / len(relevant_chunk_keys)
```

우리는 정답 청크가 **케이스당 1개**라서 이 값은 0 또는 1이 되고,
전체 평균은 곧 "몇 %의 질문에서 정답을 찾았나"가 된다.

**왜 5인가**: 우리가 LLM에게 주는 근거가 정확히 5개이기 때문이다
([quiz_generation.py:97](../../app/application/quiz_generation.py) `search_results[:5]`).
**6등이면 LLM이 아예 못 보므로 못 찾은 것과 같다.**
지표를 실제 사용 조건과 일치시킨 것이다.

### 5.4 MRR@5 (Mean Reciprocal Rank)

**"정답이 몇 등이었나"**를 본다. `1/등수`의 평균.

```python
# app/application/search/evaluation.py:43-50
for rank, chunk_key in enumerate(retrieved_chunk_keys[:k], start=1):
    if chunk_key in relevant_chunk_keys:
        return 1 / rank
return 0.0
```

| 정답 순위 | RR 값 |
|---|---|
| 1등 | 1.000 |
| 2등 | 0.500 |
| 3등 | 0.333 |
| 5등 | 0.200 |
| 못 찾음 | 0.000 |

### 5.5 두 지표가 왜 둘 다 필요한가

**Hit@5는 "찾았나"만 본다. MRR은 "잘 찾았나"를 본다.**

```text
질문 26개 모두 정답이 5등  → Hit@5 = 1.0,  MRR = 0.20
질문 26개 모두 정답이 1등  → Hit@5 = 1.0,  MRR = 1.00
```

Hit@5는 둘 다 만점이지만 실제 품질은 하늘과 땅 차이다.

**우리 시스템에서 MRR이 왜 실질적으로 중요한가**:
정답 청크가 5등이면 LLM에게 주는 5개 중 나머지 4개는 관련성이 낮은 청크다.
LLM은 5개를 다 보고 **어느 것으로 문제를 만들지 스스로 고른다.**
관련 없는 청크가 많으면 엉뚱한 걸로 문제를 만들 확률이 올라간다.

> **주의 — 이건 정직하게 말해야 한다**: "MRR이 1.0이면 문항 품질도 1.0"은 **아니다.**
> MRR은 정답 청크 하나의 순위만 본다. 나머지 4개가 좋은지 나쁜지는 안 본다.
> MRR이 높으면 **좋은 근거가 포함될 확률이 올라가는 것**이지, 비례하지 않는다.
> 그래서 근거 품질을 따로 재는 지표를 만들었다(5.6절).

### 5.6 근거 품질 지표 — 우리가 직접 정의한 것

**코드**: [evidence_quality.py](../../app/application/search/evidence_quality.py)

Hit@5/MRR은 표준 지표라 **"정답 청크"만** 본다.
그런데 우리의 진짜 관심사는 **"검색된 5개가 문제 만들기에 쓸 만한가"**다.

```python
# app/application/search/evidence_quality.py:49-58
def _is_usable(content: str) -> bool:
    stripped = content.strip()
    return len(stripped) >= 50 and stripped.endswith((".", "!", "?"))


def _is_heading_fragment(content: str) -> bool:
    return bool(_HEADING_PATTERN.match(stripped)) or not stripped.endswith(...)
```

4개 값을 낸다:

| 지표 | 의미 |
|---|---|
| `retrieved_count` | 검색된 청크 수 (보통 5) |
| `usable_evidence_count` | **50자 이상 + 문장으로 끝남** = 근거로 쓸 만함 |
| `distinct_evidence_count` | 중복 제거 후 개수 |
| `heading_fragment_count` | 제목 조각으로 보이는 개수 |

**이 지표가 청크 병합 개선의 근거였다.**
1권 3.4절에서 `usable 21/35(60%) → 32/35(91%)`가 바로 이 값이다.

지표의 한계도 기록해뒀다:

> `"heading_fragment은 병합된 청크가 여전히 제목 줄로 시작하면 정규식이 매치돼
> 완전히 0으로 안 떨어진다 — 측정 지표의 한계이며 실제 근거 품질은
> usable_evidence_count로 판단해야 한다."`

**자기가 만든 지표의 한계를 문서에 남긴 것**도 발표에서 쓸 수 있다.

## 7. 가중치 실험 — 발표의 하이라이트

여기가 **"제대로 실험했다"를 보여주는 부분**이다.
세 가지 설정을 비교했으니 반드시 구분해서 말해야 한다.

| 이름 | 설정 | 용도 |
|---|---|---|
| **A (현재 운영)** | BM25 0.7 / FAISS 0.3, k=60 | 실제 서비스 설정 |
| **B (검색 후보)** | BM25 0.8 / FAISS 0.2, k=10 | 검색 지표 최적화로 찾은 후보 |
| **C (생성 비교용)** | BM25 0.9 / FAISS 0.1, k=20 | 문항 품질 비교 실험용 |

### 7.1 문제: 정형 질문으로는 변별이 안 된다

기존 평가 세트(`search_cases_v2.json`)는 교과서 용어를 그대로 쓴 질문이다.

| 방식 | Hit@5 | MRR@5 |
|---|---:|---:|
| BM25 단독 | 100% | 0.9615 |
| 하이브리드 A | 100% | 0.9167 |

**Hit@5가 이미 100%라 천장에 닿았다.** 더 개선할 여지가 없어서 비교가 무의미하다.

### 7.2 해법: 패러프레이즈 세트를 만들었다

같은 정답 청크를 향하되 **일상어로 바꿔 쓴 질문 26개**를 새로 작성했다.

```text
원래:        "환율이 상승하면 국내 물가에 어떤 영향을 줄 수 있는가?"
패러프레이즈: "해외 돈의 값이 오르면 우리가 사는 물건값도 오를 수 있는 이유는 무엇인가?"
```

**이게 좋은 실험 설계인 이유**: 의미 검색이 유리해야 하는 조건을 일부러 만든 것이다.
"우리 시스템에 유리한 조건"이 아니라 **"약점이 드러나는 조건"**을 설계했다.

측정 (`verify_paraphrase_current_20260824.json`):

| 방식 | Hit@5 | MRR@5 |
|---|---:|---:|
| BM25 단독 | 96.2% | 0.8538 |
| **FAISS 단독** | **57.7%** | **0.4019** |
| 하이브리드 A | 92.3% | 0.8109 |
| 하이브리드 B | **96.2%** | **0.8782** |

**충격적인 결과가 두 개다.**

1. **일상어 질문에서도 FAISS가 57.7%로 BM25(96.2%)에 크게 뒤진다.**
   의미 검색이 유리해야 할 조건인데도 그렇다.
2. **하이브리드 A(92.3%)가 BM25 단독(96.2%)보다 낮다.**
   FAISS를 섞어서 오히려 손해를 봤다.

후보 B는 두 지표 모두 개선했다. 여기서 멈췄으면 "B로 바꾸자"가 결론이었을 것이다.

### 7.3 그런데 멈추지 않았다 — 홀드아웃 검증

**핵심 문제**: B는 **패러프레이즈 세트를 보면서 고른 값**이다.
그 세트에서 잘 나오는 건 당연하다. 이걸 **과적합(overfitting)**이라고 한다.

그래서 **B를 고를 때 한 번도 쓰지 않은 새 질문 26개**를 별도로 작성해서
설정을 고정한 채 다시 측정했다.

`verify_holdout_current_20260824.json` / `verify_holdout_candidate_20260824.json`:

| 방식 | Hit@5 | 성공 | MRR@5 |
|---|---:|---:|---:|
| BM25 단독 | 84.6% | 22/26 | 0.6744 |
| FAISS 단독 | 50.0% | 13/26 | 0.4263 |
| 하이브리드 A (현재) | **84.6%** | **22/26** | 0.6212 |
| 하이브리드 B (후보) | **80.8%** | **21/26** | **0.7000** |

**결과가 뒤집혔다.**

- B는 MRR은 올렸다 (0.6212 → 0.7000). 찾은 건 더 위로 올렸다.
- **하지만 Hit@5가 떨어졌다** (84.6% → 80.8%). **질문 하나를 더 놓쳤다.**

### 7.4 그래서 채택하지 않았다 — 판단 근거

**"MRR 상승 < Hit@5 하락"**이라고 판단했다.

이유: 우리 서비스에서 검색 실패는 **문항 생성 실패**를 뜻한다.
근거를 못 찾으면 문제를 아예 못 만든다.
반면 MRR이 조금 낮은 건 "정답 근거가 3등에 있다" 정도이고, LLM은 5개를 다 본다.

> **"찾긴 찾는데 순위가 낮은 것"보다 "아예 못 찾는 것"이 훨씬 치명적이다.**

그래서 **운영 설정을 바꾸지 않았다.**

> **발표에서 이렇게 말하면 된다**:
> "가중치 튜닝으로 개발 세트에서는 Hit@5와 MRR을 둘 다 개선한 후보를 찾았습니다.
> 그런데 그 후보를 고를 때 쓰지 않은 홀드아웃 질문 26개로 다시 검증했더니
> Hit@5가 오히려 떨어졌습니다. 개발 세트에 과적합된 값이라고 판단해서 채택하지 않았고,
> 현재 운영 설정을 유지했습니다."
>
> **이건 "성능을 못 올렸다"가 아니라 "잘못된 개선을 막았다"는 얘기다.**
> 지표를 올리는 것보다 지표에 속지 않는 게 어렵다.

### 7.5 구조적 원인 분석

7.2절에서 "하이브리드 A가 BM25 단독보다 낮다"는 이상한 결과가 왜 나왔나?
**RRF 점수를 직접 계산하면 답이 나온다** (1권 7.3절과 동일한 계산).

```text
BM25 20위 단독 점수 = 0.7 / (60 + 20) = 0.00875
FAISS  1위 단독 점수 = 0.3 / (60 +  1) = 0.00492
```

**FAISS가 1등으로 꼽은 청크조차 BM25 20등보다 점수가 낮다.**
후보 풀이 20개이므로, **FAISS만 발견한 청크는 최종 top-5에 들어올 수 없다.**

동시에 FAISS는 순위를 흔든다:

```text
BM25 1위, FAISS 미발견 = 0.7/61          = 0.011475
BM25 8위, FAISS 1위    = 0.7/68 + 0.3/61 = 0.015212   ← 역전
```

**결론**: 현재 설정에서 FAISS는 **리콜을 늘리지 않고 순위만 재조정**한다.
"의미 검색으로 키워드 검색의 누락을 보완한다"는 일반적인 설명이
**우리 실제 설정에서는 성립하지 않는다.**

이게 하이브리드 A가 BM25 단독보다 Hit@5가 낮게 나온 이유다.
새 정답을 못 찾으면서 기존 정답 순위만 흔들었기 때문이다.

> **이 분석이 강한 이유**: 실험 결과를 관찰하는 데 그치지 않고
> **왜 그런지 산술적으로 증명**했다. 수식 두 줄로 재현 가능하다.

### 7.6 그래서 앞으로 뭘 할 것인가 (개선 과제)

정직한 결론은 이렇다.

1. **가중치 조정만으로는 해결이 안 된다.** 홀드아웃에서 확인됐다.
2. 근본 원인은 **FAISS 자체의 성능**이다 (패러프레이즈 57.7%, 홀드아웃 50.0%).
3. 그래서 개선 순서는:
   - 임베딩 입력 문맥 개선 (현재는 `heading + content`. 상위 계층 제목까지 넣어보기)
   - 임베딩 모델 업그레이드 (`text-embedding-3-large`)
   - 그 다음에 가중치 재튜닝

**순서가 중요하다.** FAISS 자체가 약한 상태에서 가중치만 올리면 노이즈만 늘어난다.

## 8. 문항 품질 평가 — 자동 통과율의 함정

**출처**: `quiz_weight_quality_comparison_20260824.md`

검색이 아니라 **최종 산출물(문항)의 품질**을 잰 실험이다.

### 8.1 실험 설계

- 동일 주제 10개, 동일 모델·검증 로직
- 설정 A (0.7/0.3, k=60) vs 설정 C (0.9/0.1, k=20)
- 로컬 dry-run (BE 전송 없음)

### 8.2 자동 검증 통과율 — 차이 없음

| 설정 | 요청 | 성공 | 통과율 |
|---|---:|---:|---:|
| A (현재) | 10 | 9 | 90.0% |
| C (후보) | 10 | 9 | 90.0% |

**여기서 멈추면 "차이 없음"이 결론이다. 그런데 사람이 직접 봤다.**

### 8.3 사람 검토 — 완전히 다른 그림

등급: **A**=수정 없이 사용 가능 / **B**=수정 필요 / **C**=배포 불가

| 설정 | A | B | C |
|---|---:|---:|---:|
| 0.7/0.3, k=60 | 2 | 5 | 3 |
| 0.9/0.1, k=20 | 3 | 2 | **5** |

**자동 통과율은 둘 다 90%인데, 실제로 바로 쓸 수 있는 건 10개 중 2~3개다.**

### 8.4 이 실험의 핵심 발견

> **"자동 검증 통과율 90%가 실제 배포 가능률 90%를 의미하지 않는다."**

통과했지만 실제로는 문제였던 사례들:

| 문제 | 구체적 사례 |
|---|---|
| 인용이 주장을 뒷받침 못 함 | 분산투자 문항에 `"펀드는 펀드매니저가 운용한다"` 인용 |
| 비현실적 시나리오 | `"3개월에 100만 원을 150만 원으로"` |
| 복수 정답 | `"고정 금리"`와 `"장기 고정 금리"`가 동시에 선택지 |
| 영어 혼용 | `"자금의 purpose에 따라"` |
| 주제 범위 축소 | `"네 가지 분류"`를 묻는데 두 분류만 다룸 |

**이 발견이 2권 5.2~5.5절의 검증 강화로 이어졌다.**

> **발표 포인트 (매우 중요)**: 이 실험은 **"우리 자동 검증의 한계를 우리가 찾아낸 것"**이다.
> "90% 통과했습니다"로 끝내지 않고 사람이 10개를 다 읽어서
> "실제로는 2~3개만 쓸 수 있다"를 확인했다.
> 자기 시스템의 약점을 스스로 계량화한 사례로 쓸 수 있다.
>
> 물론 **한계도 같이 말해야 한다**: "10문항을 한 명이 한 번 평가한 진단값이지
> 통계적 지표는 아닙니다."

조사 문제가 드러나지 않았다.

**실제 LLM이 만든, 복잡한 조사가 붙은 문장에서만 나타나는 버그**였다.

> 나머지 2건은 실제로 근거가 부실해서 계속 차단됐습니다.
> 그래서 저희는 검증 로직을 바꿀 때 **단위 테스트 + 실데이터 배치**를 같이 돌립니다."

### 9.4 최종 재검증

## 10. 알려진 한계 — 먼저 말하는 게 낫다

발표에서 이걸 먼저 말하면 신뢰가 올라간다.
지적당하고 인정하는 것보다 훨씬 낫다.

### 10.1 평가 데이터 규모

- 검색 평가: 세트당 **26문항**. 통계적으로 작다.
- 문항 품질: **10문항 × 1인 평가**. 통계 지표가 아니라 진단값이다.
- 정답 청크가 케이스당 1개라 Hit@5가 사실상 이진값이다.

**왜 이 규모인가**: 정답지를 사람이 직접 만들어야 한다.
26개도 교과서를 읽어가며 청크를 지정한 결과다.
**한계를 알면서 감수한 선택**이지 몰라서 방치한 게 아니다.

### 10.2 LLM 비결정성

같은 입력으로 두 번 돌리면 다른 문항이 나온다.
7장의 가중치 비교에는 **검색 차이와 생성 변동이 섞여 있다.**

원 리포트에도 적어뒀다:
> `"LLM 생성은 비결정적이므로 이 비교에는 검색 가중치 차이와 생성 변동이 함께 포함된다."`

**제대로 하려면**: 같은 설정으로 여러 번 생성해 평균을 내거나,
검색 결과를 고정한 뒤 생성 변동만 분리해야 한다.

### 10.3 한국어 형태소 처리

`_normalize_content_words()`의 조사 제거는 **단순 접미사 매칭**이다.
용언 활용은 처리 못 한다.

```text
"발행" vs "발행하는"   → 여전히 다른 단어로 취급
```

제대로 하려면 이 검증에도 Kiwi를 넣어야 한다.
비용 대비 효과를 보고 **알려진 한계로 남겨둔 상태**다.

### 10.4 SCENARIO 수치 검증의 공백

2권 2.3절에서 다뤘듯, SCENARIO는 코드 수치 검증을 통째로 건너뛴다.
가상 설정과 금융 사실을 정규식으로 구별할 수 없기 때문이다.

**대응**: LLM 검증에 위임 + **사람 검수 필수**.
실제로 대단원 SCENARIO 문항은 전부 수동 검수 후 게시했다.

### 10.5 FAISS가 제 역할을 못 함

7.5절에서 산술적으로 증명한 내용.
현재 가중치에서 FAISS는 리콜 확장이 아니라 재정렬만 한다.
**이건 인지하고 있고, 개선 과제 목록에 있다.**

## 11. 예상 질문 대비 — 즉답 준비

### Q1. "검색이 잘 되는지 어떻게 알았나요?"

> 정답 청크를 사람이 지정한 26문항 평가 세트로 Hit@5와 MRR@5를 측정했습니다.
> Hit@5는 상위 5개 안에 정답이 있는지, MRR은 정답이 몇 등인지를 봅니다.
> 상위 5개를 기준으로 한 건 LLM에게 실제로 5개를 주기 때문이고,
> 6등이면 못 찾은 것과 같기 때문입니다.
> 현재 정형 질문 기준 하이브리드 Hit@5 100%, MRR 0.9167입니다.

### Q2. "하이브리드 검색이 정말 도움이 됐나요?"

> **정직하게 말하면, 현재 설정에서는 검색 지표상 우위를 확인하지 못했습니다.**
> BM25 단독 MRR이 0.9615, 하이브리드가 0.9167로 오히려 낮습니다.
> 원인을 분석해보니 RRF 가중치 0.7/0.3과 k=60에서
> FAISS 1위 점수(0.00492)가 BM25 20위 점수(0.00875)보다 낮아서,
> FAISS만 찾은 청크는 최종 5개에 들어올 수 없는 구조였습니다.
> 즉 현재 FAISS는 리콜 확장이 아니라 재정렬 역할만 하고 있고,
> 이건 저희가 계산으로 확인한 뒤 개선 과제로 등록해둔 상태입니다.

### Q3. "그럼 가중치를 바꾸면 되지 않나요?"

> 실제로 해봤습니다. RRF 상수를 1,5,10,20,40,60,100까지 바꿔가며 탐색했고,
> k=10에 0.8/0.2가 개발 세트에서 가장 좋았습니다.
> 패러프레이즈 세트에서 Hit@5 92.3%→96.2%, MRR 0.811→0.878로 둘 다 올랐습니다.
> **그런데 그 값을 고를 때 쓰지 않은 홀드아웃 질문 26개로 다시 재보니
> Hit@5가 84.6%→80.8%로 떨어졌습니다.** 개발 세트 과적합이라고 판단했고,
> 검색 실패는 문항 생성 실패로 직결되므로 MRR 상승보다 Hit@5 하락이 더 위험하다고 보아
> 운영 설정을 유지했습니다.

### Q4. "LLM이 만든 문제를 LLM으로 검증하는 게 신뢰할 수 있나요?"

> **신뢰하지 않기 때문에 3단으로 나눴습니다.**
> 1단은 코드 규칙 검증입니다. 인용문이 원문에 글자 하나 다르지 않게 존재하는지,
> 선택지 형식이 맞는지, 근거에 없는 영단어가 섞였는지를 정규식과 문자열 비교로 봅니다.
> 확률이 아니라 결정적입니다.
> 2.5단은 정규식으로 금융 수치가 근거에 있는지 봅니다.
> LLM 검증은 마지막 3단이고, 코드로 표현할 수 없는 것 —
> 논리적 타당성, 복수 정답 가능성 —만 담당합니다.
> **LLM 검증은 1차 방어선이 아니라 마지막 안전망입니다.**

### Q5. "환각(hallucination)은 어떻게 막았나요?"

> 프롬프트로 부탁하는 대신 **스키마로 불가능하게 만들었습니다.**
> 검색 결과가 나온 뒤에 그 청크들의 문장만 허용하는 Pydantic 모델을 런타임에 생성하고,
> OpenAI structured output으로 강제합니다.
> 특히 chunk_key와 evidence_text를 **청크별로 한 쌍으로 묶어서** Union으로 만들었습니다.
> 두 필드를 따로 제약하면 "A청크 키 + B청크 문장" 조합이 가능해지는데,
> 쌍으로 묶으면 그 조합 자체가 스키마상 존재하지 않습니다.

### Q6. "테스트는 충분한가요?"

> 523개 중 516개가 통과하고 7개는 실제 MySQL 통합 테스트라 환경변수로 게이팅해뒀습니다.
> **다만 단위 테스트만으로는 부족하다는 걸 실제로 경험했습니다.**
> 인용 관련성 검증을 추가하고 실제 API로 16건을 돌렸더니
> 정상 문항 4건이 오차단됐습니다. 원인은 한국어 조사 처리에서
> `"의"`와 `"이다"`가 목록에서 빠진 것이었고, 테스트 픽스처는 단순한 문장이라
> 이 문제가 드러나지 않았습니다.
> 고친 뒤 4건 중 2건이 통과로 바뀌고, 나머지 2건은 실제로 근거가 부실해서
> 계속 차단됐습니다.
> 그래서 **검증 로직을 바꿀 때는 단위 테스트와 실데이터 배치를 같이 돌립니다.**

### Q7. "자동 검증 통과율이 90%면 90%를 쓸 수 있는 건가요?"

> **아닙니다. 그게 저희가 찾은 가장 중요한 문제입니다.**
> 10문항을 두 설정으로 생성해 자동 통과율을 재니 둘 다 90%였는데,
> 사람이 직접 읽어보니 수정 없이 쓸 수 있는 건 10개 중 2~3개였습니다.
> 통과했지만 실제로는 인용문이 정답을 뒷받침하지 못하거나,
> 3개월에 50% 수익 같은 비현실적 시나리오이거나,
> 선택지 둘이 포함 관계여서 복수 정답인 경우들이었습니다.
> 이 발견을 바탕으로 인용 관련성, 선택지 포함 관계, 영어 혼용,
> 집계 주장 검증을 추가했습니다.

### Q8. "왜 text-embedding-3-small인가요?"

> 세 가지입니다. 첫째 비용 — 3-large 대비 6.5배 저렴한데,
> 저희는 청킹 규칙을 바꿀 때마다 831개 전량을 재임베딩해서 실험 반복 비용이 중요했습니다.
> 둘째 차원 — 1536 대 3072라 인덱스 크기와 검색 시간이 절반입니다.
> **셋째가 핵심인데, 측정해보니 거기가 병목이 아니었습니다.**
> 하이브리드 Hit@5가 이미 100%여서 FAISS를 개선해도 최종 지표가 올라갈 여지가 없었고,
> 실제 병목은 청킹 품질이었습니다. 청크 병합으로 근거 사용률을 60%에서 91%로 올렸습니다.
> 다만 패러프레이즈 평가에서 FAISS 단독 성능이 낮게 나온 만큼,
> 임베딩 입력 문맥 개선과 모델 업그레이드는 현재 개선 과제로 두고 있습니다.

### Q9. "청크 크기는 어떻게 정했나요?"

> 고정 크기로 자르지 않고 문서 구조를 따랐습니다.
> 교과서는 번호 계층(제N장 / N.N / N))을 인식해 제목을 하위 문단에 전파하고,
> 뉴스는 2000자 이하면 기사를 통째로 하나로 둡니다.
> **다만 문단 단위로 자르니 전체의 27.8%가 제목만 있는 50자 미만 조각이었습니다.**
> 검색에는 걸리는데 근거로는 쓸 수 없는 것들이라,
> 50자 미만이면서 문장부호로 끝나지 않는 청크를 다음 청크에 병합하는 규칙을 넣었습니다.
> 1126개가 831개로 줄었고(26.4% 감소, 진단했던 27.8%와 거의 일치),
> 근거 사용률이 60%에서 91%로 올랐습니다.

### Q10. "이 프로젝트에서 가장 어려웠던 건 뭔가요?"

> **지표에 속지 않는 것이었습니다.**
> 가중치를 튜닝해서 개발 세트에서 Hit@5와 MRR을 둘 다 올린 후보를 찾았을 때,
> 거기서 멈췄으면 "성능 개선했습니다"라고 발표했을 겁니다.
> 그런데 그 값을 고를 때 안 쓴 홀드아웃 세트로 다시 재보니 결과가 뒤집혔습니다.
> 마찬가지로 자동 검증 통과율 90%도 그대로 믿었으면 문제를 못 찾았을 텐데,
> 10문항을 직접 읽어보니 실제 사용 가능한 건 2~3개였습니다.
> **측정값이 좋게 나왔을 때 한 번 더 의심하는 게 제일 어려웠습니다.**

### 검색 지표 한눈에

| 세트 | BM25 | FAISS | 하이브리드(현재) | 하이브리드(후보) |
|---|---:|---:|---:|---:|
| 정형 Hit@5 | 100% | — | **100%** | 100% |
| 정형 MRR@5 | 0.9615 | 0.7673 | **0.9167** | 0.9615 |
| 패러프레이즈 Hit@5 | 96.2% | 57.7% | **92.3%** | 96.2% |
| 패러프레이즈 MRR@5 | 0.8538 | 0.4019 | **0.8109** | 0.8782 |
| **홀드아웃 Hit@5** | 84.6% | 50.0% | **84.6%** | **80.8%** ← 하락 |
| 홀드아웃 MRR@5 | 0.6744 | 0.4263 | **0.6212** | 0.7000 |

### 한 문장씩

1. **두 종류의 검증** — pytest는 "버그가 없나", 성능 평가는 "품질이 어느 수준인가". 섞어 말하면 안 된다.
2. **Protocol 포트** — 외부 의존을 추상화해서 테스트 가능하게 설계. 난수·시각까지 주입한다.
3. **회귀 테스트** — 실제 터진 버그를 박제. 완화 수정에는 반대 방향 테스트를 쌍으로 넣는다.
4. **Hit@5와 MRR@5** — 찾았나 vs 잘 찾았나. 상위 5개인 건 LLM에게 5개를 주기 때문.
5. **근거 품질 지표** — 표준 지표가 못 보는 "검색된 5개가 쓸 만한가"를 직접 정의. 60%→91% 개선의 근거.
6. **홀드아웃 검증** — 개발 세트에서 좋아진 가중치가 홀드아웃에서 뒤집혔다. 과적합을 잡아내고 채택하지 않았다.
7. **RRF 구조 분석** — FAISS 1위(0.00492) < BM25 20위(0.00875). 현재 설정에서 FAISS는 재정렬만 한다.
8. **자동 통과율 ≠ 배포 가능률** — 둘 다 90%였지만 사람이 보니 2~3개. 이 발견이 검증 강화로 이어졌다.
9. **실데이터 검증 필수** — 523개 테스트를 다 통과한 상태에서도 조사 처리 버그가 있었다. 실제 16건 배치로 발견.
10. **한계를 먼저 말한다** — 26문항 규모, LLM 비결정성, 형태소 처리, SCENARIO 수치 공백, FAISS 성능.
