## 읽는 순서 추천

**처음 읽을 때 (2~3시간)**
1권 → 2권 → 3권을 순서대로. 각 권 끝의 "요약 — 외울 것"만 먼저 훑고 본문으로 돌아와도 좋다.

**발표 직전 복습 (30분)**
- 각 권의 마지막 "요약 — 외울 것" 절
- [3권 11장 예상 질문 대비](03-testing-and-evaluation.md#11-예상-질문-대비--즉답-준비) (Q1~Q10)
- [3권 부록 발표 30초 요약](03-testing-and-evaluation.md#부록-발표-30초-요약)

## 이 시스템을 한 문장으로

> 금융 교과서를 검색 가능한 청크로 나누고, 키워드 검색과 의미 검색을 결합해
> 근거를 찾은 뒤, **그 근거만으로** 퀴즈를 생성하고 3단계로 검증하는 파이프라인.

```text
원문 → 청킹 → BM25·FAISS 색인 → 하이브리드 검색(상위 5개)
     → LLM 생성(스키마 제약) → 코드 검증 → 중복 검증 → LLM 근거 검증
     → 출처 조립 → Spring BE(DRAFT) → 사람 검수 → 게시
```

| 항목 | 값 |
|---|---|

| 후보 풀 → 최종 | 각 **20개** → **5개** |

| 근거 사용률 개선 | 60% → **91%** |

## 이 프로젝트에서 자랑할 만한 것 3가지

발표에서 시간이 부족하면 이 셋만 말해도 된다.

**1. 환각을 프롬프트가 아니라 스키마로 막았다**
검색 결과가 나온 뒤 그 청크의 문장만 허용하는 타입을 런타임에 만들고,
chunk_key와 evidence_text를 쌍으로 묶어 교차 조합 자체를 불가능하게 했다.
→ [2권 3장](02-quiz-generation.md#3--llm-호출--스키마로-강제하기)

**2. 측정으로 병목을 찾아 고쳤다**
"근거 품질이 낮다"는 느낌을 지표로 계량화(27.8% 제목 조각) → 병합 규칙 구현
→ 재측정(근거 사용률 60%→91%). 감이 아니라 숫자로 움직였다.
→ [1권 3.4절](01-rag-pipeline.md#34-merge_short_chunks--실측으로-고친-진짜-문제)

**3. 지표에 속지 않았다**
가중치 튜닝으로 개발 세트 지표를 올렸지만, 홀드아웃 세트에서 뒤집혀 채택하지 않았다.
자동 검증 통과율 90%도 사람이 직접 읽어보니 실제 사용 가능은 2~3개였다.
→ [3권 7장](03-testing-and-evaluation.md#7-가중치-실험--발표의-하이라이트),
[3권 8장](03-testing-and-evaluation.md#8-문항-품질-평가--자동-통과율의-함정)
