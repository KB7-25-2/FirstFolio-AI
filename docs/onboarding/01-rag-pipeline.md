# 온보딩 1권 — RAG 검색 파이프라인

> 이 문서는 "원문 텍스트가 들어와서 검색 결과가 나오기까지"를 다룬다.
> 검색 결과로 문항을 만드는 부분은 [2권](02-quiz-generation.md),
> 테스트와 성능 측정은 [3권](03-testing-and-evaluation.md)에 있다.

---

## 0. 먼저: 우리가 왜 RAG를 쓰는가

### 0.1 문제 정의

우리가 만들려는 것은 **금융교육 퀴즈**다. 여기엔 두 가지 요구가 동시에 걸린다.

1. 문항이 **사실이어야 한다.** 금융 교육에서 틀린 정보는 그냥 오답이 아니라 사고다.
2. 문항의 **출처를 댈 수 있어야 한다.** "이 문제는 어디서 나왔냐"에 답할 수 있어야 검수·게시가 가능하다.

LLM에게 그냥 "예금과 적금 차이 문제 만들어줘"라고 하면 둘 다 실패한다.
모델이 학습 데이터에서 기억을 끄집어내 그럴듯하게 지어내기 때문이다(환각, hallucination).
그리고 지어낸 내용은 출처가 없다.

### 0.2 RAG가 하는 일

RAG는 **Retrieval-Augmented Generation**, 우리말로 "검색으로 보강한 생성"이다.
구조는 단순하다.

```text
[기존 방식]
질문 → LLM → 답변            (모델의 기억에 의존, 출처 없음)

[RAG]
질문 → 검색 → 관련 문서 조각 → LLM(문서 조각과 함께) → 답변 + 출처
```

핵심은 **"모델의 기억을 쓰지 말고, 내가 준 문서만 보고 답해라"**로 작업을 바꾸는 것이다.
이렇게 하면

- 모델이 지어낼 여지가 줄고 (근거가 눈앞에 있으니)
- 어느 문장을 근거로 썼는지 되짚을 수 있고 (출처가 생기고)
- 우리 교과서를 바꾸면 결과도 따라 바뀐다 (모델 재학습 불필요)

### 0.3 그래서 RAG의 성능은 두 부분으로 나뉜다

```text
전체 품질 = 검색이 올바른 근거를 가져왔는가 × LLM이 그 근거를 제대로 썼는가
              └─ 1권(이 문서)                    └─ 2권
```

이게 곱셈이라는 점이 중요하다. **검색이 엉뚱한 문서를 가져오면 LLM이 아무리 좋아도 끝이다.**
근거에 없는 내용으로 문제를 만들 수는 없기 때문이다.
그래서 우리는 검색 품질을 별도로 측정한다(3권).

## 1. 전체 지도

먼저 큰 그림을 한 번 보고, 그다음 각 단계를 하나씩 파고든다.

```text
┌─ 색인 시점 (문서를 등록할 때 미리 해두는 작업) ─────────────────┐
│                                                                 │
│  TXT 원문                                                        │
│    ↓  ① S3 업로드 (원본 보관, 버전 관리)                          │
│    ↓  ② 문서 유형별 청킹 (교과서 / 뉴스 / 일반)                    │
│    ↓  ③ MySQL 청크 저장                                          │
│    ↓  ④-A BM25 색인 (Kiwi 형태소 분석 → 단어 통계)                │
│    ↓  ④-B FAISS 색인 (OpenAI 임베딩 → 벡터)                       │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘

┌─ 검색 시점 (문항을 만들 때마다 실행) ──────────────────────────────┐
│                                                                 │
│  주제 텍스트 (예: "예금과 적금의 차이")                            │
│    ↓                                                            │
│    ├─ BM25 검색   → 상위 20개 후보                                │
│    └─ FAISS 검색  → 상위 20개 후보                                │
│    ↓  ⑤ RRF 융합 (두 순위표를 하나로 합침)                        │
│    ↓                                                            │
│  최종 상위 5개 청크 → 2권(문항 생성)으로                           │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘
```

**색인 시점과 검색 시점을 분리한 이유**는 비용과 속도다.
임베딩(문서를 벡터로 바꾸는 것)은 OpenAI API 호출이라 돈과 시간이 든다.
831개 청크를 매번 임베딩하면 문항 하나 만들 때마다 831번 API를 호출해야 한다.
그래서 **한 번 계산해서 FAISS 인덱스 파일로 저장해두고**, 검색할 때는 질문 하나만 임베딩한다.

## 2. ① 문서 등록과 원본 보관

**코드**: [document_registration.py](../../app/application/document_registration.py)

등록 흐름은 이렇게 생겼다.

```python
# app/application/document_registration.py:58-67
version_id = upload_text_object(...)      # 1) S3에 원본 업로드
stored_content = download_text_object(...) # 2) 방금 올린 걸 다시 내려받음
```

### 왜 올리고 나서 다시 내려받는가?

처음 보면 낭비 같다. 하지만 의도된 설계다.

**"우리가 청킹한 텍스트가 S3에 실제로 저장된 그 텍스트와 100% 같음"을 보장**하기 위해서다.
메모리에 있는 `content`를 그냥 쓰면, 업로드 과정에서 인코딩이 틀어지거나 잘려도 알 수 없다.
나중에 "이 청크의 원문 보여줘"라고 했을 때 S3에서 꺼낸 내용과 DB 청크가 다르면 근거 추적이 깨진다.

이건 나중에 나올 **인용 검증**(2권)과 직결된다.
우리는 "인용 문장이 청크 안에 글자 하나 다르지 않게 존재하는가"를 코드로 검사한다.
그 청크의 출처가 S3 원본과 다르면 이 검증 전체가 무의미해진다.

### 트랜잭션 경계

```python
# app/application/document_registration.py:69-107
connection = create_mysql_connection(...)
try:
    document_id = ...create_in_transaction(...)   # 문서 메타데이터
    chunks = ...chunk(source_document)            # 청킹
    ...replace_document_chunks_in_transaction(...)# 청크 저장
    connection.commit()
except Exception:
    connection.rollback()
```

문서 메타데이터와 청크는 **한 트랜잭션**으로 묶는다.
청킹 중 예외가 나면 문서 행도 같이 롤백된다.
"문서는 등록됐는데 청크가 0개"인 유령 상태를 만들지 않기 위해서다.

단, S3 업로드는 트랜잭션 밖이다. 이건 한계다.
DB가 롤백돼도 S3 객체는 남는다. 다만 S3는 버전 관리가 켜져 있고
DB에 참조가 없으면 그냥 고아 객체로 남을 뿐 서비스에 영향은 없어서 감수한 선택이다.

## 3. ② 청킹 — 이 프로젝트에서 가장 중요한 설계 결정

### 3.1 청킹이란 무엇이고 왜 하는가

문서 하나가 100페이지짜리 교과서라고 하자. 이걸 통째로 LLM에 넣을 수 없다.

- 토큰 제한에 걸린다
- 넣을 수 있어도, 100페이지 중 어디를 근거로 썼는지 특정할 수 없다
- 비용이 폭증한다

그래서 **문서를 검색·인용 가능한 단위로 쪼갠다**. 이 조각이 청크(chunk)다.

**청크 크기의 트레이드오프**가 핵심이다.

| 청크가 너무 작으면 | 청크가 너무 크면 |
|---|---|
| 문맥이 잘려서 의미를 잃음 | 관련 없는 내용이 섞여 들어감 |
| "제1장 예금" 같은 제목만 남음 | 인용 문장을 특정하기 어려움 |
| 검색에 걸려도 근거로 못 씀 | 토큰 비용 증가 |

우리는 이 트레이드오프에서 **실제로 문제를 겪었고, 측정해서 고쳤다.** 3.4절에서 다룬다.

### 3.2 문서 유형별 청커 — 왜 하나로 안 했나

**코드**: [chunkers/registry.py](../../app/application/chunkers/registry.py)

```python
# app/application/chunkers/registry.py:22-31
def create_default_chunker_registry() -> DocumentChunkerRegistry:
    paragraph_chunker = ParagraphChunker()
    return DocumentChunkerRegistry(
        chunkers={
            "textbook": TextbookChunker(paragraph_chunker),
            "news": NewsChunker(paragraph_chunker),
        },
        fallback_chunker=paragraph_chunker,   # 모르는 유형은 일반 문단 청킹
    )
```

이유는 **문서 유형마다 "의미 단위"가 다르기 때문**이다.

- **교과서**: `제3장 → 3.1 → 1)` 같은 번호 계층이 있다. 이 계층이 문맥의 핵심이다.
  "만기 전에 해지하면 약정 금리보다 낮은 금리가 적용된다"는 문장은,
  그 위에 `정기예금`이라는 제목이 있어야 무슨 얘긴지 안다.
- **뉴스**: 계층이 아니라 `헤더 / 핵심 내용 / 키워드 / 출처 유의사항` 고정 구조다.
  헤더에는 언론사·발행일·원문 URL이 들어 있고, 이건 **출처 표기에 필수**다.
- **그 외**: 빈 줄 기준 문단 분리로 폴백.

레지스트리 패턴을 쓴 이유는, 나중에 법령·약관 같은 유형이 추가돼도
`chunkers` 딕셔너리에 한 줄 추가하면 되고, **등록되지 않은 유형은 자동으로 안전한 폴백**을 타기 때문이다.
`registry.get()`은 `dict.get(key, fallback)` 한 줄이다 — 없으면 예외가 아니라 폴백.

> **면접·발표에서 나올 질문**: "왜 LangChain의 RecursiveCharacterTextSplitter를 안 썼나?"
> 답: 그건 글자 수 기준으로 자른다. 교과서의 번호 계층이나 뉴스 헤더 구조를
> 인식하지 못해서, 제목과 본문이 엉뚱하게 갈린다.
> 우리 데이터는 구조가 명확해서 구조를 이용하는 편이 이득이었다.

### 3.3 TextbookChunker — 제목 계층 전파

**코드**: [chunkers/textbook.py](../../app/application/chunkers/textbook.py)

```python
# app/application/chunkers/textbook.py:11-16
_CHAPTER_HEADING_PATTERN    # "제3장 ..." 또는 "III. ..."
_SECTION_HEADING_PATTERN    # "3.1 ..." 또는 "3. ..."
_SUBSECTION_HEADING_PATTERN # "1) ..."
```

동작을 그림으로 보면:

```text
원문                          청크에 붙는 heading / metadata
────────────────────────────────────────────────────────────
제3장 예금과 적금          →  chapter=예금과 적금
  3.1 정기예금             →  chapter=예금과 적금, section=정기예금
    본문 문단 A            →  heading="정기예금"     ← 상위 제목이 전파됨
    본문 문단 B            →  heading="정기예금"
  3.2 정기적금             →  chapter=예금과 적금, section=정기적금
    1) 자유적립식          →  ... subsection=자유적립식
    본문 문단 C            →  heading="자유적립식"   ← 가장 구체적인 것 우선
```

핵심 두 줄:

```python
# app/application/chunkers/textbook.py:44
heading = subsection_heading or section_heading or chapter_heading
```

**가장 구체적인 제목을 우선**한다. `1) 자유적립식`이 있으면 그걸 쓰고, 없으면 `3.2 정기적금`,
그것도 없으면 `제3장 예금과 적금`으로 내려간다.

그리고 새 상위 제목이 나오면 하위를 초기화한다:

```python
# app/application/chunkers/textbook.py:34-42
if 챕터 매치:
    chapter_heading = ...; section_heading = None; subsection_heading = None
elif 섹션 매치:
    section_heading = ...; subsection_heading = None
```

이걸 안 하면 `제4장`으로 넘어갔는데 `3.2 정기적금`이라는 이전 섹션 제목이 계속 따라붙는다.

### 3.4 merge_short_chunks — 실측으로 고친 진짜 문제

**코드**: [chunkers/merge.py](../../app/application/chunkers/merge.py)

이게 이 프로젝트에서 **측정 → 문제 발견 → 수정 → 재측정**을 제대로 한 사례다.
발표에서 쓸 수 있는 가장 좋은 재료다.

#### 문제

교과서를 빈 줄 기준으로 자르면 이런 청크가 대량 생성된다.

```text
청크 #12: "3.2 정기적금"                    ← 12자. 제목만 있음
청크 #13: "1) 자유적립식"                   ← 8자
청크 #14: "정기적금은 매월 일정 금액을..."    ← 실제 내용
```

`#12`, `#13`은 **검색에는 걸리는데 근거로는 쓸 수 없다.**
"정기적금"이라는 단어가 있으니 BM25가 상위로 올린다. 그런데 LLM에게 주면
`"3.2 정기적금"` 이 6글자로 문제를 만들라는 셈이다. 만들 수가 없다.

실측 결과 **전체 청크의 27.8%가 이런 조각**이었다.
즉 검색 상위 5개 중 1~2개가 쓸모없는 자리를 차지하고 있었다.

#### 규칙

```python
# app/application/chunkers/merge.py:58-62
def _should_merge_forward(content: str) -> bool:
    stripped = content.strip()
    return len(stripped) < 50 and not stripped.endswith((".", "!", "?"))
```

**50자 미만 AND 문장부호로 끝나지 않음** → 다음 청크에 병합.

`AND`인 게 중요하다. 둘 중 하나만 쓰면 오작동한다.

- 길이만 보면: "금리는 돈의 가격이다." (12자, 완결된 문장)이 병합돼버린다
- 문장부호만 보면: 마침표 없이 끝나는 긴 본문 문단이 전부 병합돼 거대 청크가 생긴다

두 조건을 다 만족해야 "제목·목차처럼 생긴 조각"이다.

#### 병합 후 처리

```python
# app/application/chunkers/merge.py:41-53
for sequence, group in enumerate(groups):
    anchor = group[0]     # 첫 청크(제목)를 기준으로
    last = group[-1]      # heading·metadata는 마지막 것을 씀
    merged_chunks.append(replace(anchor,
        chunk_key=f"{anchor.document_id}:{sequence}",  # 키 재발급
        content="\n\n".join(...),
        heading=last.heading,
        metadata=last.metadata,
    ))
```

두 가지 미묘한 결정이 있다.

1. **`heading`은 마지막 청크 것을 쓴다.** 제목 전파 로직이 이미 그룹 안 모든 청크에
   값을 채워놨고, 가장 구체적인 값이 뒤에 온다.
2. **`chunk_key`를 다시 매긴다.** 병합하면 개수가 줄어드니 `document_id:0,1,2,...`를
   연속되게 다시 붙인다. 이건 MySQL 저장 규칙(`chunk_key = "{document_id}:{chunk_order}"`,
   [mysql_chunk.py:254](../../app/infrastructure/repositories/mysql_chunk.py))과 맞추기 위해서다.

**부작용**: 재청킹하면 모든 `chunk_key`가 바뀐다.
그래서 검색 평가 케이스에 `relevant_text`(정답 문장 원문)를 같이 저장해두고,
`find_chunk_key_by_text()`로 새 코퍼스에서 정답 청크를 다시 찾을 수 있게 해뒀다
([evaluation.py:158](../../app/application/search/evaluation.py)). 3권에서 다시 나온다.

#### 결과 (실측)

`data/local/evaluation/search_quality_baseline_v4_113_20260821.json`

| 지표 | 개선 전 | 개선 후 |
|---|---:|---:|
| 전체 청크 수 | 1,126 | 831 (−26.4%) |
| 문장으로 안 끝나는 짧은 조각 | 다수 | **0** |
| 쓸 만한 근거 비율 (7개 문제 주제) | 21/35 (60%) | **32/35 (91%)** |

**"진단했던 27.8%와 실제 감소율 26.4%가 거의 일치"**한 것도 의미가 있다.
문제를 정확히 진단했다는 뜻이다.

> **발표 포인트**: 여기서 강조할 건 숫자가 아니라 **과정**이다.
> "근거 품질이 낮은 것 같다"는 느낌 → `evidence_quality` 지표로 계량화
> → 27.8%라는 진단 → 병합 규칙 구현 → 60%→91% 재측정.
> 이게 "AI가 알아서 해줬어요"와 구별되는 지점이다.

### 3.5 NewsChunker — 검증이 먼저

**코드**: [chunkers/news.py](../../app/application/chunkers/news.py)

뉴스는 청킹보다 **형식 검증**이 먼저다.

```python

    ("문서유형", "document_type"), ("제목", "title"), ("언론사", "publisher"),
```

**왜 이렇게 빡빡한가?** 뉴스는 저작권과 출처 표기가 걸린다.
`source_url`과 `published_at` 없이 등록된 뉴스로 문항을 만들면,
나중에 "이 문제 출처가 뭐냐"에 답할 수 없다.
**등록 시점에 막는 게 생성 시점에 발견하는 것보다 훨씬 싸다.**

크기 처리도 다르다.

```python
# app/application/chunkers/news.py:55-64
if len(full_content) <= self._max_chars:   # 2000자
    return [단일 청크]                       # 기사 통째로 하나
```

**2000자 이하면 기사를 자르지 않는다.**
뉴스는 교과서와 달리 기사 하나가 이미 하나의 완결된 맥락이다.
쪼개면 "누가 무엇을 했다"가 앞 청크에, "그 결과 어떻게 됐다"가 뒷 청크에 갈라져

2000자를 넘으면 섹션(`핵심 내용`/`키워드`/`출처 유의사항`) 경계로 자르되,
각 섹션의 앞부분 문단(첫 섹션 3개, 나머지 2개)은 **항상 붙여둔다**(`leading_count`).
기사 도입부가 잘려나가지 않게 하는 장치다.

## 4. ③ 저장 — searchable_text의 분리

**코드**: [domain/chunk.py](../../app/domain/chunk.py)

작지만 중요한 설계가 하나 있다.

```python
# app/domain/chunk.py:18-23
def searchable_text(self) -> str:
    """색인용 텍스트. 인용·근거 검증에는 content를 그대로 써야 하므로,
    이 값은 BM25 토큰화·FAISS 임베딩 입력에만 사용한다."""
    if self.heading:
        return f"{self.heading}\n{self.content}"
    return self.content
```

**색인에 쓰는 텍스트와 인용에 쓰는 텍스트를 분리했다.**

- **색인용 (`searchable_text`)** = `heading + content`
  → "정기예금"이라는 제목 단어가 본문에 없어도 검색에 걸리게 한다.
- **인용용 (`content`)** = 원문 그대로
  → 인용 문장이 청크 안에 있는지 검사할 때, 제목이 섞여 있으면 안 된다.

이걸 안 나누고 `heading + content`를 통째로 저장했다면,
LLM이 제목 줄을 인용 문장으로 골라올 수 있고, 그게 "원문에 있는 문장"으로 통과해버린다.
2권의 인용 검증이 뚫리는 구멍이 된다.

## 5. ④-A BM25 색인 — 키워드 검색

### 5.1 BM25가 뭔가

BM25는 **단어 빈도 기반 검색 랭킹 함수**다. 구글 이전 시대부터 쓰인 고전이고, 지금도 강력하다.

직관은 세 가지다.

1. **질문의 단어가 문서에 많이 나오면 점수가 높다** (TF, 단어 빈도)
2. **단, 흔한 단어는 값이 싸다** (IDF, 역문서빈도)
   — "금융"은 우리 교과서 전체에 나오니 변별력이 없다. "가처분소득"은 몇 군데만 나오니 값지다.
3. **긴 문서는 불리하게 보정한다** — 길면 아무 단어나 우연히 들어 있을 확률이 높으니까

우리는 `rank_bm25` 라이브러리의 `BM25Okapi`를 쓴다
([bm25.py:29](../../app/infrastructure/search/bm25.py)).

### 5.2 Kiwi 형태소 분석 — 한국어라서 필요한 단계

**코드**: [tokenizers/kiwi.py](../../app/infrastructure/tokenizers/kiwi.py)

BM25는 "단어 목록"을 입력으로 받는다. 영어는 띄어쓰기로 자르면 끝이다.
한국어는 그게 안 된다.

```text
"예금의"  "예금은"  "예금이"  "예금을"
   ↑ 띄어쓰기로 자르면 전부 다른 단어가 된다
   ↑ 질문에 "예금이"라고 쓰면 "예금의"가 있는 문서를 못 찾는다
```

한국어는 **교착어**라서 명사 뒤에 조사가 계속 붙는다.
그래서 형태소 분석기로 어간을 뽑아야 한다.

```python
# app/infrastructure/tokenizers/kiwi.py:5-25
searchable_tag_prefixes = ("N", "VV", "VA", "VX", "M", "XR", "SL", "SH", "SN")

def tokenize(self, text: str) -> list[str]:
    return [token.form.lower()
            for token in self._kiwi.tokenize(text)
            if token.tag.startswith(self.searchable_tag_prefixes)]
```

**품사 필터가 핵심이다.** 이 접두사들이 무슨 뜻인지:

| 태그 | 의미 | 예 | 왜 포함했나 |
|---|---|---|---|
| `N` | 명사 (NNG/NNP/NNB…) | 예금, 금리, 만기 | 검색어의 주력 |
| `VV` | 동사 | 상승하다, 적용되다 | "금리가 오르면" 같은 질문 |
| `VA` | 형용사 | 높다, 낮다 | "금리가 높은" |
| `VX` | 보조용언 | 있다, 지다 | 서술 구조 보존 |
| `M` | 관형사·부사 | 매우, 각 | 약하지만 변별에 기여 |
| `XR` | 어근 | 안정, 유동 | "안정적" → "안정" |
| `SL` | 외국어 | ETF, MMF | 금융 약어가 여기 걸린다 |
| `SH` | 한자 | 利子 | 교과서에 한자 병기 있음 |
| `SN` | 숫자 | 3, 2026 | "3개월", "만 65세" |

**빠진 것들이 더 중요하다**: 조사(J), 어미(E), 문장부호(S* 중 SF/SP 등).
`은/는/이/가/을/를`, `-습니다/-하고` 같은 것들은 모든 문서에 다 나오므로
검색에 아무 도움이 안 되고 노이즈만 늘린다.

> **예상 질문**: "왜 Mecab이나 Okt가 아니라 Kiwi인가?"
> 답: (1) 순수 Python 설치로 끝나서 Docker 이미지에 C++ 빌드 의존성이 안 붙는다.
> (2) 신조어·복합명사 처리가 최신이고 금융 용어 분해가 상대적으로 정확하다.
> (3) 품사 태그를 세밀하게 주므로 위 같은 필터링이 가능하다.

### 5.3 BM25 인덱스 구축

```python
# app/infrastructure/search/bm25.py:22-29
tokenized_chunks = [self._tokenizer.tokenize(chunk.searchable_text())
                    for chunk in self._chunks]
self._index = BM25Okapi(tokenized_chunks)
```

**831개 청크 전부를 토큰화해서 메모리에 올린다.**
BM25는 파일로 저장하지 않고 서버 기동 시 DB에서 읽어 매번 재구축한다
([quiz_mvp.py:32-36](../../app/quiz_mvp.py)).

왜 저장 안 하나? 831개 청크 토큰화는 몇 초면 끝나고 API 비용이 0이다.
반대로 FAISS는 API 호출 비용이 있어서 반드시 저장한다. **비용 구조가 달라서 결정이 다르다.**

점수가 0인 결과는 아예 버린다:

```python

if score_value > 0:
    results.append(...)
```

겹치는 단어가 하나도 없는 청크를 순위표에 넣으면 RRF 융합 때 노이즈가 된다.

## 6. ④-B FAISS 색인 — 의미 검색

### 6.1 임베딩이 뭔가

임베딩은 **텍스트를 숫자 벡터로 바꾸는 것**이다.
`text-embedding-3-small`은 문장 하나를 1536개 실수의 배열로 만든다.

핵심 성질: **의미가 비슷한 문장은 벡터 공간에서 가까이 놓인다.**

```text
"만기 전에 해지하면 금리가 낮아진다"     → [0.021, -0.15, 0.33, ...]
"중도 해지 시 약정 이율보다 낮게 적용"   → [0.019, -0.14, 0.31, ...]  ← 가깝다
"주식 거래는 증권사를 통해 이루어진다"   → [-0.42, 0.08, -0.11, ...]  ← 멀다
```

**단어가 하나도 안 겹쳐도** 의미가 같으면 가깝다.
이게 BM25가 절대 못 하는 일이고, FAISS를 넣은 이유다.

### 6.2 FAISS 설정 — IndexFlatIP + L2 정규화

**코드**: [search/faiss.py](../../app/infrastructure/search/faiss.py)

```python
# app/infrastructure/search/faiss.py:34-35
self._index = faiss.IndexFlatIP(vectors.shape[1])
self._index.add(vectors)

# app/infrastructure/search/faiss.py:196
faiss.normalize_L2(vectors)
```

두 가지를 이해해야 한다.

**(1) `IndexFlatIP`의 `Flat` = 정확 탐색(brute force)**

FAISS에는 근사 탐색 인덱스(`IVF`, `HNSW` 등)가 있다. 수백만 벡터에서 빠르게 찾으려고
정확도를 조금 포기하는 구조다. 우리는 **831개**밖에 없다.
근사할 이유가 전혀 없고, `Flat`은 항상 정확한 답을 준다.

> **예상 질문**: "확장성은?"
> 답: 831 → 수만 개까지는 Flat으로 충분하다(선형 스캔이지만 벡터 연산이라 빠르다).
> 수십만을 넘어가면 `IndexIVFFlat`으로 바꿔야 한다.
> 지금 단계에서 근사 인덱스를 넣는 건 조기 최적화이고, 정확도만 잃는다.

**(2) `IP`(내적) + `normalize_L2` = 코사인 유사도**

내적(inner product)은 벡터의 크기에 영향을 받는다.
긴 문서의 벡터가 크면 내용과 무관하게 점수가 높아진다.
그래서 **모든 벡터를 길이 1로 정규화**하면, 내적이 정확히 코사인 유사도가 된다
(`cos θ = (a·b) / (|a||b|)`인데 `|a|=|b|=1`이면 `cos θ = a·b`).

결과: **방향(의미)만 비교하고 크기(길이)는 무시**한다. 우리가 원하는 동작이다.

질문 벡터도 똑같은 `_prepare_vectors()`를 통과시켜 정규화한다
([faiss.py:139](../../app/infrastructure/search/faiss.py)). 이게 어긋나면 점수 체계가 깨진다.

### 6.3 왜 text-embedding-3-small인가

발표에서 반드시 나올 질문이다. 근거는 세 가지다.

1. **비용**: `3-large` 대비 약 6.5배 저렴하다. 우리는 재색인을 자주 한다
   (청킹 규칙을 바꿀 때마다 831개 전량 재임베딩). 실험 반복 비용이 곧 개발 속도다.
2. **차원**: 1536차원. `3-large`는 3072차원이라 FAISS 인덱스 크기와 검색 시간이 2배가 된다.
3. **실측상 병목이 아니었다**: 우리 측정에서 FAISS 단독 Hit@5는 0.923(v3 기준)인데
   **하이브리드가 이미 1.0**이었다. 임베딩 모델을 키워서 FAISS를 개선해도
   최종 지표가 올라갈 여지가 없었다. 병목은 임베딩 품질이 아니라 **청킹 품질**이었고,
   그건 3.4절에서 실제로 해결했다.

> 이 3번이 가장 강한 논거다. "더 좋은 모델을 안 썼다"가 아니라
> **"측정해보니 거기가 병목이 아니어서 다른 데를 고쳤다"**는 얘기다.

### 6.4 인덱스 저장·복구와 정합성 검사

FAISS는 파일 2개로 저장된다.

```python
# app/infrastructure/search/faiss.py:58-73
faiss.write_index(self._index, str(index_file))     # 벡터 본체 (.faiss)
mapping_file.write_text(json.dumps({"chunk_keys": self._chunk_keys}))  # 순서→chunk_key (.json)
```

**매핑 파일이 왜 필요한가?** FAISS는 벡터에 번호(0,1,2,...)만 매긴다.
"3번 벡터가 어느 청크인지"는 모른다. 그 대응표가 매핑 파일이다.

그래서 **둘의 순서가 어긋나면 완전히 엉뚱한 청크가 반환된다.**
소리 없이 틀린 결과가 나오는, 제일 위험한 종류의 버그다. 그래서 로드할 때 검사한다:

```python
# app/infrastructure/search/faiss.py:117-118
if index.ntotal != len(chunk_keys):
    raise ValueError("FAISS 인덱스의 벡터 수와 청크 키 수가 일치하지 않습니다.")
```

한 단계 더 있다. **MySQL 청크 수와 FAISS 벡터 수도 비교**한다
([index_health.py](../../app/application/search/index_health.py)).

여기서 **의도적으로 두 가지 다른 행동**을 한다.

```python
# app/application/search/index_health.py:29-38
def ensure_index_matches_corpus(...):
    """검색 품질 측정처럼 정확한 일치가 필요한 곳에서만 사용한다.
    운영 서비스 기동 경로는 check_index_matches_corpus로 경고만 남기고 계속 진행한다."""
```

| 경로 | 불일치 시 동작 | 이유 |
|---|---|---|
| 품질 측정 (`search_quality_mvp`) | **예외로 중단** | 틀린 숫자를 리포트에 남기면 안 됨 |
| 서비스 기동 (`quiz_mvp`) | **경고만 찍고 계속** | 일부 검색이 누락돼도 서비스는 떠야 함 |

이 구분은 실제 사고에서 나왔다.
`search_quality_baseline_v3_20260820.json`을 보면
`"재색인 전에는 doc_id=98(실용금융, 108청크)가 FAISS에서 누락돼 있었음"`이라고 기록돼 있다.
**108개 청크가 벡터 검색에서 통째로 빠진 채 측정하고 있었던 것**이다.
이 검사를 넣은 뒤로 같은 사고가 조용히 지나가지 않는다.

## 7. ⑤ 하이브리드 검색과 RRF — 이 파이프라인의 심장

**코드**: [search/hybrid.py](../../app/application/search/hybrid.py)

### 7.1 왜 둘을 섞는가

두 검색은 서로 반대의 약점을 가진다.

| | BM25 | FAISS |
|---|---|---|
| **강점** | 정확한 용어 일치. 전문용어에 강함 | 표현이 달라도 의미로 찾음 |
| **약점** | 단어가 안 겹치면 못 찾음 | 애매하게 비슷한 걸 끌어옴 |
| **예시** | "가처분소득" 질문 → 정확히 그 청크 | "쓸 수 있는 돈" → 가처분소득 청크 |

우리 실측(`verify_paraphrase_current_20260824.json`, 일상어로 바꿔 쓴 질문 26개):

| 방식 | Hit@5 | MRR@5 |
|---|---:|---:|
| BM25 | 0.962 | 0.854 |
| FAISS | 0.577 | 0.402 |
| 하이브리드 | 0.923 | 0.811 |

**우리 데이터에서는 BM25가 압도적으로 강하다.** 이건 인정하고 가야 하는 사실이다.
왜 그런지는 7.4절에서 정면으로 다룬다.

### 7.2 RRF 공식

RRF는 **Reciprocal Rank Fusion**, "역순위 융합"이다.

```python
# app/application/search/hybrid.py:59, 79
rank_score = self._settings.bm25_weight  / (rrf_k + rank)   # 0.7 / (60 + 순위)
rank_score = self._settings.faiss_weight / (rrf_k + rank)   # 0.3 / (60 + 순위)
```

같은 청크가 양쪽에 다 나오면 **점수를 더한다**:

```python
# app/application/search/hybrid.py:61-63
scores_by_chunk_key[chunk_key] = scores_by_chunk_key.get(chunk_key, 0.0) + rank_score
```

#### 왜 점수가 아니라 순위를 쓰는가 — 이게 RRF의 핵심

BM25 점수는 `0 ~ 30` 같은 범위고, FAISS 코사인 유사도는 `-1 ~ 1`이다.
**스케일이 완전히 다르다.** 그냥 더하면 BM25가 항상 이긴다.
정규화(min-max, z-score)를 시도할 수도 있지만, 질문마다 점수 분포가 달라서
"이번 질문에서 BM25 최고점이 5점"인 경우와 "30점"인 경우를 공정하게 비교할 방법이 없다.

**순위는 스케일이 없다.** 1등은 어느 엔진에서든 1등이다.
그래서 순위만 쓰면 두 엔진을 안전하게 섞을 수 있다. 이게 RRF가 널리 쓰이는 이유다.

#### `rrf_k = 60`이 하는 일

`1/rank`를 그냥 쓰면 1등과 2등 차이가 너무 크다 (`1.0` vs `0.5`, 2배).
분모에 상수를 더하면 **상위권이 완만해진다**.

```text
k=0  (그냥 1/rank):  1등 1.000, 2등 0.500, 3등 0.333   ← 1등 독식
k=60 (우리 설정):     1등 0.0164, 2등 0.0161, 3등 0.0159 ← 상위권 비슷비슷
```

의도: **"어느 한쪽에서 1등"보다 "양쪽에서 고르게 상위권"인 청크를 우대**한다.
두 검색이 독립적으로 동의한 결과가 더 믿을 만하다는 가정이다.
`60`은 RRF 원논문(Cormack et al., 2009)의 기본값이고 관행적으로 널리 쓰인다.

#### 후보 풀(20)과 최종(5)의 분리

```python
# app/application/search/hybrid.py:29-47
candidate_top_k = 20   # 각 엔진에서 20개씩 가져와서
...
# app/application/search/hybrid.py:101
return combined_results[:5]   # 융합 후 5개만 반환
```

각 엔진에서 5개씩만 가져오면 **융합할 여지가 없다.**
BM25 7등이지만 FAISS 1등인 좋은 청크가 아예 후보에 없으니까.
넓게 뽑아서(20) 섞고 좁게 내보낸다(5).

### 7.3 가중치가 실제로 무슨 일을 하는가 — 직접 계산해보자

이건 **내가 직접 검증한 내용**이고, 발표에서 가장 강한 카드다.

현재 설정 `BM25 0.7 / FAISS 0.3 / k=60`으로 점수를 계산하면:

```text
BM25만 발견한 청크          FAISS만 발견한 청크
  1등  → 0.011475             1등  → 0.004918
  5등  → 0.010769             5등  → 0.004615
 10등  → 0.010000            20등  → 0.003750
 20등  → 0.008750
```

여기서 나오는 결론:

> **FAISS 1등(0.004918) < BM25 20등(0.008750)**
>
> 즉, **BM25가 20등으로라도 찾아낸 청크는, FAISS가 1등으로 꼽은 청크보다 항상 위에 온다.**
> BM25가 5개 이상 결과를 내놓는 한, **FAISS만 발견한 청크는 최종 top-5에 들어갈 수 없다.**

그럼 FAISS는 아무 일도 안 하는가? 아니다. **양쪽이 다 찾은 청크를 끌어올린다.**

```text
BM25 1등, FAISS 미발견        = 0.7/61            = 0.011475
BM25 8등, FAISS 1등           = 0.7/68 + 0.3/61   = 0.015212  ← 역전!
```

**정리하면 현재 설정에서 FAISS의 역할은 "새로운 문서를 발굴하는 것"이 아니라
"BM25가 찾은 문서들의 순위를 재조정하는 것"이다.**

이게 실측 데이터와 정확히 맞아떨어진다.
패러프레이즈 세트에서 하이브리드 Hit@5(0.923)가 BM25 단독(0.962)보다 **낮았다.**
FAISS가 순위를 흔들어서 BM25가 top-5에 넣었던 정답 하나를 밀어냈다는 뜻이다.

> **발표에서 이렇게 말하면 된다**:
> "가중치 0.7/0.3과 k=60을 넣고 산술적으로 계산해보면, FAISS 단독 1위가 BM25 20위보다
> 점수가 낮습니다. 그래서 현 설정에서 FAISS는 리콜을 늘리는 역할이 아니라
> BM25 결과를 재정렬하는 역할을 합니다. 이건 저희 실측에서도 확인됐는데,
> 하이브리드 Hit@5가 BM25 단독보다 오히려 낮게 나온 케이스가 그 증거입니다."

이 수준으로 답하면 "그냥 라이브러리 붙였구나"와 완전히 다르게 들린다.

### 7.4 그럼 의미 검색을 왜 넣었나 — 정면 반박 준비

**예상 질문**: "FAISS가 그 정도 역할밖에 안 하면 왜 넣었나? BM25만 쓰면 되지 않나?"

세 가지로 답한다.

**(1) 우리 서비스의 질의는 사용자 입력이 아니다**

일반 검색 서비스는 사람이 아무렇게나 치는 질문을 받는다. 거기선 의미 검색이 필수다.
그런데 우리는 다르다. 검색어가 **소단원 제목**이다.

```python
# app/application/quiz_batch.py:38
topic=sub_chapter.title,     # "예금과 적금의 차이" 같은 정형화된 제목
```

이 제목은 교과서 용어를 그대로 쓴다. 그래서 **BM25가 유리한 게 당연하다.**
이건 약점이 아니라 **우리 도메인 특성**이다. 이렇게 말할 수 있어야 한다.

**(2) 그래도 없애지 않은 이유는 "제목과 본문 용어가 다를 때"의 보험**

소단원 제목이 항상 교과서 본문 용어와 일치하지는 않는다.
예를 들어 커리큘럼 제목이 `"목돈 마련하기"`인데 교과서 본문은 `"정기적금"`이라고 쓰면
BM25는 못 찾는다. FAISS는 찾는다.
지금 커리큘럼에선 이런 경우가 드물지만, **커리큘럼은 우리가 아니라 기획이 바꾸는 값이다.**
검색 파이프라인이 제목 표현에 취약하면 그때마다 터진다.

**(3) 측정된 대가가 거의 없다**

FAISS를 붙여서 잃은 게 얼마인지 우리는 숫자로 안다.
패러프레이즈 세트에서 Hit@5 0.962 → 0.923 (26문항 중 1개 손실).
홀드아웃 세트에서는 0.846 → 0.846 (**손실 없음**).
비용은 문항당 임베딩 1회(수천분의 1센트).

**"보험료가 이 정도면 들어둘 만하다"**가 정직한 답이다.
"하이브리드가 무조건 좋아요"라고 하는 것보다 훨씬 설득력 있다.

> **정직하게 말할 것**: 만약 "그러면 FAISS 가중치를 올리면 되지 않냐"고 물으면,
> 3권에서 다룰 실험 결과가 답이다. 실제로 가중치를 바꿔봤고, 결론은
> **"패러프레이즈 세트에선 좋아졌지만 홀드아웃 세트에선 나빠졌다"**였다.
> 즉 튜닝셋에 과적합된 것이라 채택하지 않았다. (3권 5장)

### 7.5 exclude_chunk_keys — 같은 근거 재사용 방지

```python
# app/application/search/hybrid.py:85-93
excluded_chunk_keys = set(exclude_chunk_keys)
combined_results = [... for chunk_key, score in scores_by_chunk_key.items()
                    if chunk_key not in excluded_chunk_keys]
```

같은 주제로 문항을 3개 만들면, 검색 결과가 매번 똑같아서 **거의 같은 문제 3개**가 나온다.
그래서 배치에서 앞 문항이 인용한 청크를 다음 문항의 검색에서 제외한다
([quiz_batch.py:186-188](../../app/application/quiz_batch.py)).

**제외는 융합 후에 한다.** 융합 전에 빼면 순위가 밀려 올라오면서
후보 풀 20개의 구성 자체가 달라진다. 융합 후에 빼면 원래 6등이던 청크가 5등으로
자연스럽게 올라온다(테스트: `test_exclude_chunk_keys_pulls_up_next_candidate_within_pool`).

그리고 이 제외는 **같은 topic 안에서만** 적용된다
(`cited_chunk_keys_by_topic` — topic별 딕셔너리).
다른 주제 문항이 인용한 청크까지 막으면 근거가 금방 고갈된다.

### 숫자

| 항목 | 값 |
|---|---|
| 코퍼스 청크 수 | **831개** (병합 전 1,126개) |
| 교과서 문서 | 8개 (doc_id 81~86, 97, 98) |
| BM25 가중치 / FAISS 가중치 | **0.7 / 0.3** |
| RRF 상수 k | **60** |
| 후보 풀 / 최종 반환 | **각 20개 / 5개** |
| 임베딩 모델 | `text-embedding-3-small` (1536차원) |
| 청크 병합 기준 | 50자 미만 **AND** 문장부호로 안 끝남 |

### 한 문장씩

1. **RAG를 쓴 이유** — 금융 교육은 사실 정확성과 출처가 필수인데, LLM 단독으로는 둘 다 안 된다.
2. **문서 유형별 청커** — 교과서는 번호 계층, 뉴스는 헤더 구조로 의미 단위가 다르다. 모르는 유형은 문단 폴백.
3. **청크 병합** — 제목 조각 27.8% 진단 → 병합 규칙 → 쓸 만한 근거 60%→91%. 측정 기반 개선의 대표 사례.
4. **searchable_text 분리** — 색인엔 heading 포함, 인용 검증엔 content 원본. 안 나누면 인용 검증에 구멍이 생긴다.
5. **Kiwi 품사 필터** — 한국어는 교착어라 형태소 분석 필수. 조사·어미를 빼야 검색어가 깨끗해진다.
6. **IndexFlatIP + L2 정규화** — 831개엔 근사 탐색이 불필요. 정규화하면 내적이 곧 코사인 유사도.
7. **RRF** — 점수 스케일이 다른 두 엔진을 순위로만 융합. k=60은 상위권 격차를 완화해 "양쪽이 동의한 결과"를 우대.
8. **현 가중치의 실제 효과** — FAISS는 리콜 확장이 아니라 BM25 결과의 재정렬 역할. 산술로 증명 가능하고 실측과 일치.
9. **인덱스 정합성 검사** — 품질 측정은 예외로 중단, 서비스는 경고 후 진행. doc_id=98 누락 사고에서 나온 설계.
